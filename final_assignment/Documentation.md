## 1. The Idea

My idea was an easy, family-friendly 2D arcade game where the player picks an animal and catches its favourite falling food while avoiding the snacks that belong to the other pets. Matching animal to food is intuitive enough for children, which makes it family-friendly.

The original pitch :

- Four animals: Monkey, Dog, Frog, Cat
- Movement left and right along the bottom of the screen
- Randomly spawning food (Banana, Fish, Bone, Flies)
- Score up for the right food, score down or a lost life for the wrong one

Two things were left open at that stage: the **game over condition** was still a question mark in the concept, and power-ups, increasing difficulty and sound were listed as optional extras.
_____

## 2. Development Process

The project was not written in one. It was broken into small steps, each of which had to run before the next one started:

1. Window and game loop
2. Player character with left/right movement
3. A single falling object
4. Collision detection
5. Multiple objects and a spawning system
6. Matching logic (right food vs. wrong food)
7. Lives and game over
8. Tidying up

### Phase 1 

The first working version opened a window, ran a game loop and drew the player as an orange rectangle. Two structural decisions were made here and kept for the rest of the project:

- **Object-oriented approach.** `Animal` holds name, favourite food, position, speed and a `pygame.Rect` used as hitbox. 
 -> `Food` later mirrored this structure with a `fall()` method
- **Placeholders before graphics.** Every object was drawn as a colored rectangle with its name written underneath. So I could test the entire game logic before an image existed (to see if the hitbox was correct)

Understanding the game loop itself was an early hurdle: why events must be read every frame, why `screen.fill()` is needed before drawing (otherwise old frames stay visible), what `pygame.display.flip()` actually does.

### Phase 2 

The `Food` class initially had a fixed fall speed of 4. When the difficulty system was added later, this had to be changed: the speed is now passed in as a parameter when the object is created, so each new food item is created with the current speed. This was the first point where a parameter helped me to be more flexible than a hard-coded value.
Collision uses `pygame.Rect.colliderect()` -> Food that is caught cannot be deleted while looping over the list, so it is collected in a second list (`food_to_remove`) and removed afterward.

### Phase 3 Game states

The open question from the concept, what happens on game over, was answered with 3 lives, which makes a round end by itself and suits a short break better than a timer.
The single main loop was a good decision. The game tracks its current state using string constants.

### Phase 4 Restructuring into functions

The loop had grown to well and become hard to read. I split the code into functions 
`main()` now contains only the loop and calls three things per frame: handle input, update, draw.

### Phase 5 Graphics

Rectangles were replaced with images.
A dictionary was chosen over a long `if`/`elif` chain: `ANIMAL_IMAGES["Monkey"]`

### Phase 6 

Playtesting showed the game was too punishing. So I adjusted it.

- The player's favourite food now spawns with a 40 % chance
- Missing your own food costs a point, so standing still is not a valid strategy
- Difficulty scales with the score, so fall speed increases every 5 points
- A highscore is written to a text file and shown on the game over screen

---

## 4. Features Implemented

- Five playable animals, each with its own favourite food
- Start-screen with animal selection (keys 1–5)
- Left/right movement with screen boundaries
- Random food spawning (40% for favourite food)
- Collision detection through `pygame.Rect.colliderect()`
- Score and life system
- Increasing difficulty based on score
- Pause function (P)
- Game over screen with restart (R) and quit (Q)
- Highscore stored in `highscore.txt`
